# Gurindam Agents & Contribution Guide

## 1. Project Context & Philosophy

**The Origin of Gurindam** is a Unity 6.2 (`6000.2.10f1`) 3D action-roguelite hack-and-slash game.
- **Core Loop:** The Scholar navigates a fantasy realm shrouded in the dark fog of forgetfulness, wielding the *Arbiter's Brush* (melee staff combos) and *Inscribed Gurindam* (chanted text projectiles) to recover fragments of the *Gurindam Dua Belas*.
- **Death & Progression:** Defeat dissolves the protagonist into liquid ink, returning them to the *Sanctuary of the Pen* (hub area) to interact with Raja Ali Haji and the Putri Tujuh to invest *Heritage Points* into permanent upgrades.
- **Cultural Grounding:** Malay cultural heritage, classical literature, and Nusantara mythology (Cindaku, Gajah Mina, Sang Kelembai, Toyol, Durjana, Londo) are core to the game's identity.
- **Split-License Architecture:**
  - Gameplay code, systems, and tooling are licensed under **GNU GPLv3** (`LICENSE`).
  - Narrative lore, 3D models, textures, audio, and character designs are licensed under **CC BY-NC-SA 4.0** (`LICENSE-ASSETS`).

### 1.2 Work Hierarchy & Ownership

Authority runs top to bottom. When layers disagree, the higher layer wins and the agent adapts.

1. **User edits (highest authority).** Anything the user changes by hand in the Unity Editor, an IDE, or externally is authoritative. Never revert, reformat, overwrite, or "clean up" user edits. If your change would conflict with them, stop and ask; if the user has an uncommitted change, design around it.
2. **Unity auto-generated state (middle).** Unity owns `Library/`, `Temp/`, `obj/`, `Logs/`, `Gurindam.slnx`, `*.csproj`, imported artifacts, and the `.meta` files it creates for assets. Treat this layer as read-only: never hand-edit generated files, never fight the Editor's serialization, and never commit generated output. `.meta` files are Unity-generated but **versioned** — commit them with their asset; never hand-edit a GUID or delete a `.meta` to force a reimport.
3. **Agent changes (lowest authority).** Source code, scenes/prefabs edited through Unity, configuration, and documentation. The agent may modify this layer only, and only in ways that respect the two layers above. If fulfilling a request would require overriding a user edit or fabricating Unity-generated state, report the conflict instead.

Practical consequences:
- Prefer letting Unity regenerate project files over patching them yourself.
- Do not re-serialize scenes/prefabs the user did not ask you to touch.
- An agent's "fix" must never silently discard user intent; confirm before touching uncommitted user work.

## 3. Multi-Agent Orchestration Framework

To achieve high velocity without corrupting Unity project state, agents operate within a coordinated multi-agent orchestration pipeline.

```
                   +----------------------------------+
                   |   Lead Orchestrator (Conductor)  |
                   +-----------------+----------------+
                                     |
         +---------------------------+---------------------------+
         |                           |                           |
         v                           v                           v
+------------------+       +-------------------+       +--------------------+
| Lore & Narrative |       | Technical Systems |       | Unity Asset &      |
| Lorekeeper Agent |       | & Combat Agents   |       | Inspector Guardian |
+------------------+       +-------------------+       +--------------------+
         |                           |                           |
         +---------------------------+---------------------------+
                                     |
                                     v
                   +----------------------------------+
                   |     QA & Verification Agent      |
                   +----------------------------------+
```

### Agent Roles & Specialized Personas

| Role | Domain / Focus | Key Responsibilities & Tools |
| :--- | :--- | :--- |
| **Lead Orchestrator** | Task lifecycle, work breakdown, agent dispatch | Coordinates dependencies, synthesizes subagent reports, enforces architecture, owns the Git branch and final commit plan. |
| **Combat & Mechanics Agent** | `Player.cs`, `Hurtbox.cs`, hitboxes, combat math | Fluid combo mechanics, brush strikes, ranged text projectiles, frame timings, dodge invulnerability, hit-stop. |
| **Enemy AI & Encounters Agent** | `Enemy.cs`, `EnemySpawner.cs`, boss logic | Encounters, state machines/behavior trees (Toyol, Durjana, Londo, Cindaku, Gajah Mina), NavMesh pathfinding, telegraph cues. |
| **Progression & Systems Agent** | Hub state, Sanctuary upgrades, save/load | Permanent progression, Heritage Points, death-to-ink transition, inventory/stats, scene transitions, persistence. |
| **Unity Asset & Inspector Guardian** | Prefabs, scenes, `.meta`, ScriptableObjects | Protects YAML integrity, prevents GUID breakage, validates serialized field links, audits shader/URP settings. |
| **Narrative & Cultural Lorekeeper** | Gurindam text, dialogue, authenticity | Malay literary tone, respectful depiction of Raja Ali Haji / Putri Tujuh, CC BY-NC-SA compliance. |
| **QA & Verification Agent** | EditMode & PlayMode tests, regressions | Test fixtures, boundary cases (pause, respawn, null refs), per-frame GC allocation checks. |

### Model Allocation & Delegation Matrix

- **Lightweight (`flash` / `flash_lite`):** recon, broad codebase search, single-script syntax checks, documentation, boilerplate tests.
- **High-Capability (`inherit` / `pro`):** orchestration, combat state machines, boss AI, progression serialization, cross-system refactors.

## 4. Orchestration Lifecycle & Pipeline

Every non-trivial feature or refactor traverses these stages.

### Phase 0: Git Preflight (Read-Only)
- `git status` and `git branch --show-current` before touching anything.
- Confirm you are on a fresh session branch (see §8.1) and that the working tree has no unrelated changes you could overwrite.
- *Strict Rule:* Never start work on top of uncommitted work you do not own.

### Phase 1: Reconnaissance & Discovery (Read-Only)
- Inspect existing scripts, prefabs, ScriptableObjects, scenes, and test coverage before writing code.
- Identify core dependencies, interfaces (`Assets/Scripts/Interfaces/`), and regression vectors.
- *Strict Rule:* Zero file modifications during this stage.

### Phase 2: Interface & Contract Specification
- Define shared C# interfaces, event delegates, or ScriptableObject schemas first.
- Establish serialized field names and inspector requirements before behavioral logic.
- Ensure parallel subagents have non-overlapping file scopes.

### Phase 3: Parallelized Specialized Execution
- Agents execute code updates strictly within their assigned domains.
- Never allow concurrent edits to the same `.unity` scene or `.prefab` asset.
- Unity runtime constraints:
  - Zero heap allocations (`GC.Alloc`) in hot paths (`Update`, `FixedUpdate`, collision loops).
  - Cache component references in `Awake`/`Start`; `GetComponent` in `Update` is forbidden.
  - Use `NonAlloc` raycast/overlap variants and cached buffers.

### Phase 4: Asset & Metadata Synchronization
- Every new `.cs` script or asset must have its corresponding `.meta` file committed in the **same commit**.
- Never delete or recreate `.meta` files arbitrarily; preserving GUIDs prevents broken inspector references.
- If serialized fields are renamed, use `[FormerlySerializedAs("oldName")]` to prevent data loss.
- Binary assets that match `.gitattributes` LFS patterns must be committed through Git LFS; verify with `git lfs status` before committing.

### Phase 5: Verification & Gatekeeping
- Run EditMode tests for pure C# logic and PlayMode tests for physics/damage/spawner behavior where test assemblies exist.
- Verify the Unity Console is clean after import; report anything you could not verify manually.

## 5. Unity-Specific Development Practices

### Serialized Fields & Component Contracts
- Use `[SerializeField] private` instead of `public` when external exposure is unnecessary.
- Validate required references in `Awake()`/`Reset()` with `Debug.Assert` or conditional logging.
- Maintain serialized field names unless a tested `[FormerlySerializedAs]` migration exists.

### Scene & Prefab YAML Safety
- Avoid raw text edits to `.unity` and `.prefab` files unless strictly necessary (e.g. a targeted GUID fix).
- Resolve scene/prefab conflicts inside the Unity Editor, not by hand-editing YAML.
- Document component values and hierarchy changes in the final report so the user can verify them.
- After resolving an asset conflict, confirm the scene imports, references resolve, and no duplicate GUIDs exist.

### Editor vs. Runtime Separation
- Editor-only scripts live in an `Editor/` folder or editor-only assembly definitions.
- Runtime scripts must not reference `UnityEditor` except under `#if UNITY_EDITOR`.

### Generated Files
- Unity rewrites the solution (`Gurindam.slnx`), `*.csproj`, `Library/`, `obj/`, `Temp/`, and `Logs/` whenever it opens or compiles.
- These are ignored and must never be committed or manually "cleaned" while Unity is running; if you need to remove local caches, close the Editor first.

### Build & Compilation

**Unity is the only build system.** Script compilation, asset import, shader compilation, and player builds all happen through the Unity Editor (or a Unity build script the user explicitly asked you to run).

Agents must not:
- run `dotnet build`, `dotnet restore`, `dotnet test`, `msbuild`, `csc`, `xbuild`, `nuget restore`, or IDE build commands;
- compile `Assembly-CSharp` or the generated `.csproj` files outside Unity;
- invoke the Unity editor in `-batchmode`/`-executeMethod` for a build unless the user explicitly requests a build.

Rationale: the generated `.csproj`/`.slnx` are Unity outputs and are ignored; building them outside Unity can produce results that do not match the Editor's assembly definitions, package versions, or scripting define symbols.

When a compile check is needed, ask the user to compile/open the project in Unity, or rely on the Editor's own compile and report what the Console shows. Never claim a build passed based on a non-Unity compiler. If the user explicitly asks for a specific build command, run exactly that command and report its real output.

## 6. Domain-Specific Edge Cases to Guard

Every change to gameplay, enemy behavior, or progression must explicitly account for:
1. **Death & Respawn Lifecycle:** Defeat must cleanly reset combat states, cancel active projectile coroutines/tweens, and route to `PlayerDeathHandler.cs` without missing-reference exceptions.
2. **Pause & Scene Transitions:** Tweens, audio clips, and physics effects must respect `Time.timeScale` or cleanly pause/resume.
3. **Hitbox / Hurtbox Timing:** Dodge/hit i-frames must prevent multi-damage across overlapping colliders.
4. **Heritage Progression State:** Heritage Points and unlocked abilities must be idempotent and resilient to save/load interruption.
5. **Cultural Integrity:** Gurindam text, recitations, and historical-figure dialogue must remain respectful and faithful to Malay literary tradition.

## 7. Testing & Quality Verification

- **EditMode Tests:** Required for calculation logic (damage multipliers, combo chains, progression cost formulas, loot tables).
- **PlayMode Tests:** Required for component integration (spawner cycles, hurtbox collisions, death-ink trigger).
- **Verification Rule:** Never claim a test, compile check, or inspector validation passed unless it was actually executed. If a check cannot be run in this environment, report it under **Manual Verification Required**.
- **Current gap:** the project has no test assemblies yet. Adding the first EditMode assembly is a valid standalone task; until then, verification means an Editor compile with a clean Console plus the specific manual checks listed in the report.
- **Builds run in Unity only:** compile checks and player builds go through the Unity Editor. Do not substitute `dotnet build`, `msbuild`, or a test runner launched outside Unity (see §5, Build & Compilation).

## 8. Clean Git Workflow

These rules are adapted from the project's reference workflow and apply to every agent and contributor.

### 8.1 Branch per session

Every coding session begins on a new branch:

1. Inspect `git status` before changing anything.
2. Preserve existing uncommitted work; never discard or overwrite unrelated changes.
3. Create and switch to a new branch from `main`:

```text
git switch -c <type>/<short-description>
```

Use a descriptive name, for example:

```text
feat/dungeon-teleporter
fix/hurtbox-multihit
chore/gitignore-2026
docs/agents-git-workflow
assets/cindaku-animation
```

Do not work directly on `main`. Do not reuse a branch from a previous session unless the user explicitly asks.

**Unity caveat:** open Unity *before* creating the branch only if the Editor is already running. Creating a branch does not change the working tree; if Unity rewrites ignored files, they will not appear in the diff.

### 8.2 Commit after every major action

Commit after each coherent, independently reviewable unit of work. Major actions include:

- Adding or changing a gameplay script, component, or prefab behavior.
- Changing a scene, prefab, animator controller, or `ProjectSettings`.
- Adding or updating art/audio/text asset files (with their `.meta`).
- Updating `.gitignore`, `.gitattributes`, or build/tooling configuration.
- Adding or updating documentation (`AGENTS.md`, `README.md`, `docs/`).
- Adding tests or a test assembly.

Rules:

- Do not batch unrelated changes into one commit.
- Do not leave a session with uncommitted changes unless the user explicitly asks to stop.
- If a task is intentionally incomplete, commit the working increment and report the remaining work.
- Run the relevant Unity compile/tests in the Editor before committing when practical (never `dotnet build`/`msbuild`; see §5).
- Never claim a successful build or test without actually running it.

### 8.3 Commit hygiene

- Use an imperative commit subject; add a body explaining what and why when it is not obvious.
- One concern per commit. Keep `.cs` and its `.meta` together; keep scene/prefab edits together with the scripts they require.
- Do not commit generated output: `Library/`, `Temp/`, `obj/`, `Logs/`, `UserSettings/`, `.vs/`, IDE project/solution files, `*.csproj`, `*.sln`, `*.slnx`, Blender backups.
- Do not commit secrets, tokens, credentials, or local machine configuration.
- Do not rewrite history or force-push unless the user explicitly requests it.
- Do not commit binary assets as ordinary blobs when `.gitattributes` requires LFS; run `git lfs status` and confirm new binaries are queued as LFS objects.

### 8.4 Unity and LFS-specific Git rules

- **Meta files are part of the asset.** A commit that adds/moves/deletes an asset must include the matching `.meta` in the same commit. Never stage a script without its `.meta`.
- **Never regenerate GUIDs.** Do not delete `.meta` files to "fix" an import; it silently breaks scene and prefab references.
- **Scenes and prefabs merge badly.** Only one agent may edit a given `.unity`/`.prefab` at a time. If a conflict occurs, resolve it in Unity, keep both intended changes, and verify the scene loads.
- **LFS prerequisites:** `git lfs install` must have been run for the machine; fetching LFS content requires GitHub credentials. When a pull reports "smudge filter lfs failed", authenticate rather than `git lfs`-skipping the checkout, or the binary assets will remain pointer files.
- **Do not disable LFS** or commit pointer files by hand.
- **Keep the cache out of commits.** `Library/` is local-only; restoring a branch should never require it.

### 8.5 Syncing and conflicts

- Fetch and fast-forward by default:

```text
git fetch origin
git merge --ff-only origin/main
```

- Never use `git pull` with an implicit merge on a dirty tree; commit or stash first.
- When a merge conflicts:
  1. Inspect every conflicted file (`git diff --name-only --diff-filter=U`).
  2. Resolve code/text conflicts manually; resolve scenes/prefabs in Unity.
  3. Verify no conflict markers remain: `git grep -nE '^(<<<<<<<|>>>>>>>)' -- .` must return nothing.
  4. Stage resolved files and complete the merge commit.
- Never `git reset --hard`, `git clean -fd`, `git checkout --`, or delete branches/stashes without explicit user authorization (see §9).

### 8.6 Pull requests and merging

- Non-trivial work lands through a pull request against `main`; use `gh pr create` / `gh pr merge` when the task calls for it.
- Keep PRs focused; describe the gameplay/asset impact and the manual verification steps.
- Merge commits are acceptable for feature branches that need to stay in sync with `main`.
- Do not force-push a branch that others may have based work on.
- Delete merged branches only when the user asks.

### 8.7 End-of-session report

At the end of each milestone, report:

- Branch name and commits created (or the fact that work is uncommitted).
- Files created or modified.
- Architectural decisions.
- Tests/builds actually executed and their results.
- Known limitations and outstanding issues.
- Manual verification required in the Unity Editor.
- Any local files left behind (caches, backups, logs).

## 9. Version Control & Safety Boundaries

- **Zero Destructive Actions:** Never execute `git reset --hard`, `git clean -fd`, `git checkout --`, branch deletion, or stash drops without explicit user authorization.
- **Preserve Uncommitted Work:** Always verify `git status` before beginning work. Never overwrite or discard existing user modifications.
- **Atomic Commits:** Keep C# code, `.meta` files, and the assets/scenes they depend on in a clean, buildable state in the same commit.
- **No silent history rewriting:** rebases, amends of pushed commits, and force-pushes require explicit user approval.
- **Unity builds only:** never run `dotnet build`, `dotnet test`, `msbuild`, `csc`, or an IDE build unless the user explicitly asks for that exact command; Unity owns compilation and builds (§5).
- **Report rather than guess:** if a Git operation would discard or rewrite someone else's work, stop and ask.
